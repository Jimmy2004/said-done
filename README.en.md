**📋 Requirements**

- **A voice service that provides transcript text**, made up of:
  - **Recording hardware** that records audio and transcribes it to text. The author currently uses, and recommends, the XGIMI **极米记得** wristband.
  - **A host machine** that can sync the transcript text to your agent (for example, see [mnemo-push-public](https://github.com/Jimmy2004/mnemo-push-public) for syncing transcripts to your own server).
- **At least one active agent subscription**, such as ChatGPT (Codex) or Claude (Claude Code), used to screen and execute tasks.

**🚀 Let your agent set it up**: copy the whole block below and paste it into any agent that can run commands, such as Claude Code, Codex or opencode.

```text
Please install and configure the said-done MCP server (https://github.com/Jimmy2004/said-done), then walk me through the complete setup. Follow these steps in order:

1. Check the environment: confirm git and Python 3.11 or newer are installed. If anything is missing, tell me how to install it; do not install system software on your own.
2. Install: clone the repository to ~/said-done (run git pull if it already exists), create a virtual environment .venv inside it, and run .venv/bin/python -m pip install -e .
3. Initialize the config: if ~/.config/said-done/config.json does not exist, copy the repository's config.example.json there (it defaults to the mock model in screening-only mode, which is safe).
4. Register the MCP server: determine which host you are running in (Claude Code, Claude Desktop, Codex, opencode or another), and following that host's instructions in the repository's docs/AGENT_SETUP.md, register said-done as a stdio MCP server: the command is the absolute path to .venv/bin/said-done-mcp, and the environment variable SAID_DONE_CONFIG is the absolute path to the config file above. Back up any existing config file before changing it, and tell me which file you changed.
5. If the host must be restarted or the MCP server reloaded for this to take effect, tell me exactly what to do and wait for my confirmation before continuing.
6. Once connected, call said-done's get_setup_guide tool and follow the guide strictly, step by step: screening model → batching and admission rules → transcript source → execution environment → observe results in screening-only mode first. Whenever a step needs my choice, stop and ask me; do not decide for me.

Security requirements: never read the contents of the credentials txt file, and never ask me to paste an API key into the chat. Credentials must only be entered by me into the file generated by setup_begin, then imported into the OS keychain by the MCP server; explain to me why you cannot see the key.
```

said-done is a local MCP server. It reads your voice transcripts and picks out the tasks you actually meant to get done. Each candidate goes through strict validation, then gets handed to the AI execution environment of your choice. The transcript source, screening model and execution environment are all swappable, and an agent in your MCP host walks you through setup step by step.

said-done only processes transcript **text**. It does not record audio or run speech recognition.

## How it works

```text
manual input / folder / transcript MCP service / third-party source plugins
                    │
           transcript segments
                    │
       SQLite storage + heartbeat batching
                    │
   screening model decision + strict validation
                    │
   audit log → deduplication → task state machine
                    │
   preflight → task workspace → execution environment
                    │                     ▲
          artifact validation      host claim / complete
                    │
            results + audit

MCP host ⇄ stdio tools / guide://setup guide / setup prompt
                    │
  config.json + OS keychain (secrets stored separately)

Persistent scheduling: said-done run (separate background worker)
```

## Quick start

Requires Python 3.11+. Offline tests need no API, account or real CLI.

```sh
python -m venv .venv
.venv/bin/python -m pip install -e '.[test]'
mkdir -p ~/.config/said-done
cp config.example.json ~/.config/said-done/config.json
.venv/bin/said-done-mcp
# equivalent: .venv/bin/python -m said_done.mcp_server
```

The example config uses the mock classifier, manual transcript input and the mock executor. It also sets `screening_only=true`, so tasks are screened but never executed.

Once the server is connected to an MCP host, have the agent call `get_setup_guide`. It then walks through, in order: screening model → batching and admission rules → transcript source → execution environment. Run in screening-only mode for a while, and enable execution once you trust the decisions.

The MCP process does not poll on its own. For continuous operation, run a separate background worker:

```sh
.venv/bin/said-done --config ~/.config/said-done/config.json run
```

The [agent setup guide](docs/AGENT_SETUP.md) has everything else:
- the full setup steps and the credential security explanation;
- launchd / systemd templates;
- host configs for Claude Desktop, Claude Code, Codex and opencode.

It is also available as the resource `guide://setup` and the prompt `setup`.

Codex example (merge into `~/.codex/config.toml` and replace the absolute paths):

```toml
[mcp_servers.said-done]
command = "/ABS/PROJECT/.venv/bin/said-done-mcp"
[mcp_servers.said-done.env]
SAID_DONE_CONFIG = "/ABS/CONFIG/config.json"
```

The CLI works too: `submit`, `process-now`, `status`, `task-result`, `screening-audit`, and more.

- **Config location:** the MCP server reads `$SAID_DONE_CONFIG`, then `$SAID_DONE_HOME/config.json`, then defaults to `~/.config/said-done/config.json`. The CLI also accepts an explicit `--config`.
- **Shared state:** the background worker and the MCP server must use the same config and data directory.
- **Environment variables:** all use the `SAID_DONE_` prefix.

## Usage

- **Setup:** `setup_status` → import credentials, choose and test a model → `explain_screening` → transcript source → execution environment → review screening results.
- **Run:** `submit_transcript`, `process_now`, `status`, `list_tasks`, `task_result`. Getting `{"busy": true}` is normal while the background worker is running.
- **Audit:** `audit_summary`, `audit_records`. Transcript text and evidence fields are hidden by default; pass `include_evidence=true` to include them.
- **Host pull:** with the `host` executor, the scheduler runs preflight and then leaves the task for the host:
  1. The host claims it with `claim_next_task` and does the work in the task workspace.
  2. The host calls `complete_task`, which triggers artifact validation.
  3. If the host can't finish, `release_task` hands the task back.

**Default batching and admission rules:**
- Check every 600 seconds.
- Send a batch for screening when any of these holds: it reaches 200 characters, a trigger phrase appears, or the oldest segment has waited 1,800 seconds.
- Batches hold at most 50 segments.
- Quoted evidence, input paths and output paths must all pass strict validation.

Change any of these with `configure_screening`. If you're unsure, keep the defaults.

## Security model

**How credentials are stored.** API keys never appear in chat or in the config file:
1. `setup_begin` creates a txt file readable and writable only by you.
2. You fill in the key yourself.
3. The local MCP process imports the key into the OS keychain, then overwrites and deletes the txt on a best-effort basis.
4. The agent only ever sees the file path, the key's fingerprint and length, and the import status.

If no keychain is available, said-done says so explicitly and falls back to an unencrypted 0600 file. At runtime, the key is sent only to the API endpoint you configured.

**This is not absolute isolation.**
- An agent with file or shell access could technically read the txt; the setup guide forbids it.
- Other programs running as the same OS user may be able to access the keychain.
- On SSD/APFS, overwrite-then-delete cannot guarantee complete erasure.
- If you accidentally paste a key into chat, rotate it in your provider's dashboard right away.

**Protections that always apply:**
- Quoted evidence must appear verbatim in the transcript, and outputs may only be written to the workspace's `output/`.
- File tasks are preflighted, and inputs are provided as read-only copies.
- A task state machine governs every step, and a crash never triggers a blind re-run.
- Artifacts are validated after execution.
- Errors never echo transcript text or provider error bodies.

**Limits to keep in mind:**
- CLIs and hosts still have their own permissions. An executor without an OS sandbox gets no OS-level protection just because its working directory is isolated.
- Third-party transcript source plugins are local Python code; only install plugins you trust.

**Subscription disclaimer.** Before using a subscription classifier, the agent must show this disclaimer in full and get explicit consent. Only then may it set `acknowledge_subscription_risk=true`:

> You have chosen to use your personal ChatGPT/Claude subscription to process transcripts in a non-interactive way. This may violate the provider terms of service or usage policy, will consume subscription quota, and may trigger rate limiting, account suspension or other action. This project is not affiliated with, endorsed by or supported by OpenAI or Anthropic and makes no guarantees. **All consequences are your own responsibility.**

## Support status

"✅ Verified" means a real end-to-end run on macOS on 2026-11-07; everything else reflects the implemented design. The runs used codex-cli 0.166.0, Claude Code 2.1.310 and opencode 2.1.3. The MCP stdio path and macOS keychain import/delete were also verified.

### Screening models

| Classifier | Interface | Status |
|---|---|---|
| `chat-completions` | `/chat/completions` | ✅ Verified (MiniMax). For MiniMax, DeepSeek, OpenRouter and gateways |
| `openai-compatible` | OpenAI Responses API (`/responses`) | ✅ Verified (MiniMax) |
| `anthropic` | Anthropic Messages (`/v1/messages`) | ✅ Verified (MiniMax's Anthropic-compatible endpoint) |
| `codex-subscription` | Official Codex CLI, decision-program mode | ✅ Verified, defaults to `gpt-6-luna`. Requires a local login and accepting the subscription risk |
| `claude-subscription` | Official Claude CLI | ✅ Verified, defaults to `claude-haiku-5-5` |
| `mock` | Offline | For demos and tests |

The verification set has 5 transcripts:
- 2 that should be approved (a document task and a code task);
- 2 that should be rejected (small talk, and relaying what someone else said);
- 1 proposed and then cancelled in the same batch.

Every classifier above scored 5/5.

**The API format is detected by probing.** If you leave `api_style` blank when importing credentials, said-done sends minimal model-less requests to `/models`, `/chat/completions`, `/responses` and `/messages`. These cost no tokens, and the URL is never used to guess.
- If several formats work, it picks chat-completions, then openai-compatible, then anthropic, and lists the alternatives.
- A format you set explicitly is still probed; a mismatch produces a warning, not a failure.
- If probing fails, the key is still stored and the txt still deleted, and you're asked to check the URL and key or set the format by hand. Re-run detection any time with the MCP tool `probe_api`.

### Choosing models

- **Screening** is lightweight classification:
  - Both subscriptions default to the cheapest model (`gpt-6-luna`, `claude-haiku-5-5`).
  - On the standard OpenAI or Anthropic API, the agent recommends the cheapest model in the list and you confirm.
  - With any other provider, you describe the model you want in your own words; the agent finds the exact model ID and asks you to confirm it.
- **Execution** produces real documents and code, so there is no default model and the screening model is never reused. You choose, and "use the environment's own default model" is one of the options.

### Decision-program mode for the Codex subscription

Instead of returning JSON in its final message, the model answers by running a small deterministic program we provide:
- With no task, it runs `decide.py N "<reason>"`.
- With a task, it writes a draft JSON and runs `decide.py submit draft.json`. The program checks the draft with the production validator; if the draft fails, it prints hints so the model can fix it on the spot (up to 5 attempts).
- On success the program writes the result file, and the server reads it and validates it again in full.

So no matter how talkative the model is, the result is deterministic. `test_classifier` first runs a Y/N smoke program to confirm the CLI can execute at all.

**Known limitation:** OpenAI strict structured outputs reject the current task schema, which has optional fields and open dictionary fields. As a result:
- The Codex subscription doesn't pass `--output-schema` by default, and `use_response_format` for `chat-completions` should stay off. The schema lives in the prompt, and the program validates and retries.
- The built-in Codex model list is only an example; any model ID is accepted.

## Writing a transcript source plugin

A third-party package declares an entry point in its own `pyproject.toml`, and said-done discovers it automatically once installed:

```toml
[project.entry-points."said_done.sources"]
my-source = "my_package.source:MySource"
```

The entry point is a source class constructed with `(source_id, options, repository)`. Your plugin needs to:
- provide an `Options` Pydantic model for config discovery;
- implement `id`, `kind`, `poll(ctx) -> PollResult`, `status() -> dict` and `close()`, plus an optional `next_deadline(now)`;
- keep transcript text out of what `status` returns.

What the framework provides:
- `SourceContext` gives you repository writes, per-source key-value state and a clock.
- Segment IDs are namespaced per source, so different sources never collide.
- If any source returns `complete=false`, screening for that round is deferred.

Config example:

```json
{"id": "notes", "kind": "folder", "options": {"path": "/ABS/TRANSCRIPTS"}}
```

The options schema returned by `list_sources` and the [design document](docs/DESIGN.md) are authoritative. Never put credentials in plugin config.

## Design idea: have the AI run a program instead of trusting its output

> In the age of AI, ideas matter more than code.

The hardest problem in this project was not writing code; it was **models that don't follow instructions**. Ask for nothing but a JSON object, and the model adds explanations, renames fields or breaks the format, so there are always results you didn't expect. The usual fix is to keep tightening the prompt and then parse and patch the output. But that is a fight against the model's speaking habits, and it never ends.

Look at it from another angle: **whatever the model says, its goal is always to get the task done.** So don't ask it to *tell* you the answer; ask it to *run a program* that submits the answer:

- Give it a tiny, deterministic program (`decide.py` in this project). With no task, it runs `decide.py N "<reason>"`; with a task, it writes a draft and runs `decide.py submit draft.json`.
- The program validates the draft on the spot. If the draft fails, the program prints specific errors, and the model, wanting to finish the task, reads them, fixes the draft and resubmits (with a retry cap).
- On success the program writes the result file, and the server reads it and validates it again in full.

Now it no longer matters how much the model rambles: **the final result comes from the program, not from the model's output text.** Unreliable language output becomes reliable program execution. Before real use, the model first runs a small Y/N program to confirm it can actually execute commands.

The idea isn't limited to this project. Whenever a model keeps producing the wrong format or drifting off-target, try this: **write your requirements as a program and have the model get it to pass, rather than trying to persuade the model.**
